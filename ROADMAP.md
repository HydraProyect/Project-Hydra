# Roadmap — CAE Manager

Orden de construcción por dependencia real de dominio, no por número de módulo del brief. Cada fase tiene criterios de aceptación verificables; no se empieza la siguiente fase sin cerrar los de la anterior.

## Fase 0 — Fundación

Sin UI de negocio todavía visible; es la base sobre la que se apoya todo lo demás.

- Solución .NET 9 con las 4 capas (`Domain`, `Application`, `Infrastructure`, `Web`) y proyectos de test, según `ARCHITECTURE.md`.
- Modelo de datos completo (todas las entidades de `DATABASE.md`) con `IEntityTypeConfiguration`, migraciones aplicadas, datos semilla de `TipoDocumento` y `ParametroSistema` reales (los 15 tipos y los umbrales 30/15 del Excel).
- ASP.NET Core Identity configurado: login, logout, roles semilla (`Administrador`, `Supervisor`, `EjecutivoCae`, `Consulta`), policies de autorización base.
- Interceptor de auditoría + soft delete global query filter funcionando sobre al menos una entidad de prueba.
- Design tokens de `DESIGN_SYSTEM.md` como variables CSS globales + layout shell (Navbar, Sidebar, área de contenido) con modo claro/oscuro.
- Componentes core implementados y documentados en `DESIGN_SYSTEM.md`: Button, Input, Select, Badge, Card, DataTable básica, Empty State, Loading State, Toast, Modal.
- Dashboard con los seis KPIs del Excel real (Trabajadores activos, Centros/Plataformas, Documentos vencidos, Urgentes, Próximos, Vigentes) — puede mostrar datos semilla/demo en esta fase.

**Criterio de aceptación**: la aplicación arranca, un usuario puede iniciar sesión, ve el Dashboard con KPIs reales de la base de datos (no hardcodeados), y existen pruebas unitarias pasando para el cálculo de estado de Documento.

## Fase 1 — Módulo vertical de referencia: Clientes

Primer módulo de negocio completo, de punta a punta, que fija el patrón que **todos** los módulos siguientes replican literalmente.

- CRUD completo de Cliente: listar (tabla con búsqueda, orden, filtro por `EsCritico`, paginación), crear (drawer), editar, eliminar (soft delete con confirmación), ver detalle.
- Los 5 estados de página (`Loading`/`Empty`/`Error`/`Forbidden`/`Success`) implementados y verificados manualmente, no solo en teoría.
- Auditoría visible: el detalle de un Cliente muestra su historial de cambios.
- Exportar la tabla de Clientes a Excel (primer caso real de exportación, patrón reutilizable).

**Criterio de aceptación**: un usuario puede crear, buscar, editar, exportar y eliminar (soft) un Cliente sin fricción, en menos de 3 clics desde el Dashboard, con feedback claro en cada paso. Este módulo sirve de plantilla — se documenta explícitamente qué archivos/carpetas copiar como punto de partida para el siguiente módulo.

## Fase 2 — Cadena de dominio principal

En orden de dependencia (cada uno depende del anterior):

1. ✅ **Empresas** — catálogo simple, mismo patrón que Clientes.
2. ✅ **Centros** — depende de Cliente; CRUD base con selector de Cliente. `PlataformaAcceso` (credenciales cifradas) y `RequisitoDocumental` se añaden en una iteración posterior sobre el detalle de Centro, cuando ese módulo pase a página completa con secciones — no bloquean el resto de Fase 2.
3. ✅ **Trabajadores** — depende de Empresa, con validación de DNI.
4. ✅ **Tipos de Documento** — pantalla de administración sobre el catálogo semilla de Fase 0, restringida al rol Administrador (crear/editar, sin eliminar — es catálogo de configuración).
5. ✅ **Documentos** — depende de Trabajador + TipoDocumento. Subida de PDF (`IFileStorageService` sobre disco, fuera de `wwwroot`, servido solo vía endpoint autenticado) y cálculo de estado en vivo con `CalculadoraEstadoDocumento` — el mismo cálculo que usa el Dashboard, para que nunca haya dos vigencias distintas mostradas en la app. "Editar" un documento es renovarlo (nueva fecha de emisión); trabajador y tipo de documento no cambian una vez creado.
6. **Documentos Empresa** — variante a nivel Empresa en vez de Trabajador, si el Excel/negocio lo confirma como necesario al llegar aquí (revisar contra datos reales antes de construir). Pendiente — no bloquea el resto de Fase 2.
7. ✅ **Asignaciones** — depende de Trabajador + Centro. `Asignacion` no tiene soft delete en el dominio: "eliminar" es darla de baja (`FechaBaja`), preservando el historial completo — mejora directa sobre la matriz de "X" del Excel, que no guardaba fechas. La advertencia de bloqueo de acceso por `RequisitoDocumental` queda pendiente de ese módulo (ver punto 2).
8. ✅ **Alertas** — vista de solo lectura calculada en vivo sobre Documentos (Próximo/Urgente/Vencido, ordenada por severidad), no una tabla `Alerta` sincronizada por un job en segundo plano — todavía no existe infraestructura de jobs programados en el proyecto, y una vista calculada nunca puede desincronizarse del estado real. La entidad `Alerta` del dominio (con `Nivel` y `FechaGeneracionUtc`) queda preparada para cuando se necesite marcar alertas como leídas por usuario o notificar activamente; hoy no se usa. El mapeo estado→color/etiqueta se centralizó en `EstadoDocumentoUi` para que Documentos y Alertas nunca puedan mostrar el mismo estado de forma distinta.

Empresas, Centros, Trabajadores, Tipos de Documento, Documentos, Asignaciones y Alertas replican el patrón de Clientes (repositorio de agregado + Commands/Queries en Application + página con QuickGrid/Drawer/DialogoConfirmacion en Web, donde aplica) y quedaron verificados end-to-end en navegador — incluyendo, para Documentos, subida y descarga real de un PDF verificada byte a byte y el semáforo de vigencia calculado correctamente contra la fecha de emisión; para Asignaciones, el flujo completo Cliente→Centro→Empresa→Trabajador→Asignación→Baja; y para Alertas, que un documento vencido creado en Documentos aparece correctamente listado. El estilo de página de listado se extrajo a `wwwroot/css/list-page.css`. La cultura de la aplicación se fijó a `es-ES` (fechas/números) al detectar que sin configurarla explícitamente se renderizaban en formato estadounidense.

**Fase 2 completa.** El flujo completo real del Excel (dar de alta un trabajador, asignarlo a un centro, cargarle su documentación, ver su semáforo de vigencia y sus alertas) es reproducible en el sistema de principio a fin. Solo queda pendiente Documentos Empresa, condicional a confirmación de negocio — no bloquea el paso a Fase 3.

**Criterio de aceptación**: el flujo completo real del Excel (dar de alta un trabajador, asignarlo a un centro, cargarle su documentación, ver su semáforo de vigencia) es reproducible en el sistema de principio a fin.

## Fase 3 — Vistas transversales y operación diaria

- ✅ **Dashboard** con datos 100% reales y desglose por rol. Los 6 KPI base los ve cualquier rol. A partir de ahí, escalera aditiva por rol (cada uno ve lo del anterior más lo suyo): EjecutivoCae añade "Documentos que requieren atención" (top 5 vencidos/urgentes, mismo cálculo que Alertas); Supervisor añade "Centros con más riesgo" (conteo de vencidos/urgentes agrupado por Centro, vía asignaciones activas); Administrador añade "Empresas con más riesgo" (mismo conteo agrupado por Empresa contratista). Consulta ve solo los KPI base. El rol se resuelve leyendo `AuthenticationStateProvider` en el componente (no hay reglas de negocio de Application involucradas — es una decisión de presentación). Verificado en navegador con los 4 roles: cada uno ve exactamente las secciones que le corresponden y ninguna de las que no.
- ✅ **Calendario** de vencimientos: vista mensual (semana en lunes, convención española), con navegación mes anterior/siguiente y botón "Hoy". Cada día con vencimientos muestra una insignia con el recuento coloreada según el peor semáforo de ese día (mismo cálculo que Dashboard/Alertas); clic en el día abre un modal con el detalle (trabajador, tipo de documento, estado). `ObtenerVencimientosMesQuery` en Application filtra `Documento.FechaVencimiento` dentro del mes pedido. Verificado en navegador: carga del mes actual, navegación entre meses, botón "Hoy", clic en un día con datos muestra el detalle correcto, cierre del modal.
- ✅ **Reportes**: página `/reportes` con vista previa en pantalla (misma tabla/badges que Alertas) y exportación a Excel y PDF del reporte de vigencia documental — a diferencia de Alertas, incluye también los documentos Vigentes, porque es el reporte pensado para entregar a un cliente/auditor como prueba de cobertura completa, no solo lo pendiente de acción. Excel con ClosedXML (mismo patrón que Clientes, Fase 1). PDF con **PDFsharp 6** (MIT) en vez de QuestPDF (licencia por ingresos de la empresa que lo usa, inviable para un SaaS de terceros — ver `ARCHITECTURE.md`), dibujando la tabla a mano con `XGraphics` y fuente DejaVu Sans embebida como recurso del ensamblado (necesario para que PDFsharp, que no depende del SO, renderice bien los acentos del español). Verificado en navegador: vista previa con datos reales, descarga de Excel y de PDF (encabezado `%PDF-` válido, tamaño de archivo coherente, texto y acentos legibles al releer el PDF generado).

- ✅ **Buscador global** (`Cmd/Ctrl+K`) sobre Cliente/Empresa/Centro/Trabajador — reemplazo directo de la hoja "Filtros" del Excel. Overlay con búsqueda con debounce agrupada por categoría; cada resultado navega al listado del módulo con el filtro precargado (`?q=`), no a una página de detalle (todavía no existen). Verificado en navegador: atajo de teclado, clic en botón visible, búsqueda por nombre y por DNI, navegación con filtro precargado, cierre con Escape y al navegar.

  Construir esto destapó un bug real y significativo: **los toasts llevaban toda la Fase 2 sin funcionar.** El render mode de una página (`@rendermode InteractiveServer`) no se propaga hacia arriba a su `MainLayout` — todo lo que vive en el Layout fuera de `@Body` (como `<AnfitrionToasts />`) permanecía estático y nunca recibía eventos. Ningún test lo detectó porque las aserciones comprobaban la presencia del contenedor `.toast` en el HTML, no de un mensaje real. Corregido dando `@rendermode InteractiveServer` explícito a cada componente del Layout que lo necesita (ver `CODING_STANDARDS.md`). De paso se corrigió otro bug real: la `FallbackPolicy` de autorización exigía sesión iniciada también para los archivos estáticos (JS/CSS), causando una carrera real en navegaciones frescas — los `import()` dinámicos de JS no se reintentan solos. Los archivos estáticos ahora son `AllowAnonymous()`.

**Fase 3 completa.** Las cuatro vistas transversales (Dashboard con desglose por rol, Calendario, Reportes, Buscador global) están construidas y verificadas end-to-end en navegador con datos reales.

**Criterio de aceptación**: cada rol ve un Dashboard con la información que le corresponde, se puede navegar el calendario de vencimientos mes a mes, se puede exportar el estado documental completo a Excel y PDF, y se puede encontrar cualquier Cliente/Empresa/Centro/Trabajador desde cualquier pantalla en menos de tres clics (`Cmd/Ctrl+K`).

## Fase 4 — Administración y gobierno

Las cuatro pantallas de esta fase están restringidas al rol Administrador (`@attribute [Authorize(Roles = ...)]`, mismo patrón que Tipos de Documento en Fase 2).

- ✅ **Configuración**: `/configuracion` edita `ParametroSistema.UmbralAmbarDias`/`UmbralRojoDias` (antes fijos en el seed de Fase 0). Reutiliza las invariantes que el dominio ya protegía (`ParametroSistema.Actualizar`, ámbar > rojo > 0) a través de un `IParametroSistemaRepository` nuevo — fila única, sin Id explícito en la interfaz. Verificado en navegador: valores semilla 30/15 al cargar, guardar cambios, persistencia tras recargar, y que la validación de negocio (ámbar > rojo) bloquea correctamente un valor inválido sin escribir en la base de datos.
- ✅ **Auditoría** como módulo navegable en `/auditoria` (antes solo se acumulaba en la tabla `RegistroAuditoria` sin ninguna pantalla). `RegistrosAuditoria` se expuso en `IApplicationDbContext`; `ObtenerAuditoriaQuery` pagina y filtra por tipo de entidad. Application no resuelve el nombre de usuario (no conoce Identity, que vive en Infrastructure) — Web lo resuelve después vía `UserManager`, mismo principio que ya separa Login del resto de la app. Verificado en navegador: carga de registros reales generados por otras acciones de esta misma fase, filtro por tipo de entidad, paginación.
- ✅ **Usuarios**: `/usuarios`, CRUD completo sobre Identity directamente (`UserManager`/`RoleManager`), sin pasar por MediatR/Application — Identity ya es su propio sistema de persistencia, igual que Login ya hacía. Crear, editar nombre/rol, y activar/desactivar (vía `LockoutEnd`, no eliminación — coherente con el soft delete del resto de la app). Verificado en navegador, incluyendo dos casos de seguridad reales: un usuario desactivado no puede iniciar sesión, y un Administrador no puede desactivar su propia cuenta.
- ✅ **Roles**: `/roles`, vista de referencia (no CRUD dinámico) — los 4 roles están fijos y alineados 1:1 a los 4 niveles de Dashboard (ver `ARCHITECTURE.md`), así que la pantalla muestra su descripción y cuántos usuarios tiene cada uno, con enlace a Usuarios para la gestión real. Verificado en navegador.

**Fase 4 completa.**

**Criterio de aceptación**: un Administrador puede dar de alta un usuario con un rol, verificar que ese rol determina lo que ve en Dashboard, desactivar y reactivar una cuenta, ajustar los umbrales de alerta sin tocar código, y ver el historial completo de auditoría filtrado por entidad.

## Fase 5 — Importación desde Excel

✅ Completa. Se abordó al final a propósito: solo tenía sentido una vez existían todas las entidades destino. Verificada end-to-end con un archivo Excel real de un SPA (no un fixture sintético) — el archivo **no se incorporó al repositorio** porque contiene datos personales reales (nombres, DNI, fecha de nacimiento, email de trabajadores); la verificación se hizo subiéndolo directamente en un navegador real vía Playwright contra una base de datos local descartable, nunca commiteado.

- Página `/importacion` (Administrador): analizar (sin escribir nada) → revisar el plan → confirmar → reporte final. `IExcelImportacionParser` (Application) implementado con ClosedXML en Infrastructure (`ClosedXmlImportacionParser`), igual patrón de dependencia invertida que `IFileStorageService`.
- Hojas leídas: `Centros_Plataformas`, `Empleados`, `Extranjeros (Ibertec GmbH)`, `Asignaciones`. `Requisitos_Centro` y las columnas de `PlataformaAcceso` (Plataforma/Usuario/Contraseña) se omiten deliberadamente — ver Fase 2, punto 2: ese módulo de UI todavía no existe, importar esos datos sin pantalla para verlos ni gestionarlos sería peor que no importarlos. `Parametros` no se reimporta: ya quedó sembrado en Fase 0 con los mismos valores exactos de este archivo.
- Cada fila de `Centros_Plataformas` se importa como un Cliente **y** un Centro con el mismo nombre (el Excel origen fusiona ambos conceptos en una sola columna de texto libre sin separador fiable — el propio dominio ya documentaba esta normalización, ver `Centro.cs`). Los nombres que indican centro genérico, sin confirmar, o que fusionan varios centros reales (p. ej. "Refrescos Levante S.A. (genérico - planta sin confirmar)", "Bebidas del Norte S.A. (todos los centros: ...)") se importan tal cual pero se marcan como **advertencia**, con instrucción explícita de revisar y desglosar manualmente después — no se intenta adivinar el desglose.
- Detección de errores explícita, con motivo, sin abortar el resto del archivo: DNI vacío o con formato inválido, DNI duplicado dentro del propio archivo, fecha de emisión futura, tipo de documento no reconocido en el catálogo, fila de trabajador sin nombre/apellidos. Cada intento de escritura en la base de datos va además protegido con try/catch por fila — un dato inesperado no aborta el resto de una importación por lo demás válida.
- Reutiliza entidades ya existentes por nombre/DNI en vez de duplicarlas: **reimportar el mismo archivo no crea filas repetidas** (verificado explícitamente).

Dos bugs reales encontrados al verificar contra el archivo real:

1. **Falso rechazo de asignaciones por nombre.** La hoja `Asignaciones` usa nombres abreviados en la cabecera de cada columna de centro (p. ej. "Cadena Iberia"), mientras que `Centros_Plataformas` usa el nombre completo ("Cadena Industrial Iberia S.A. - Planta Norte"). El emparejamiento por texto exacto descartaba silenciosamente la mayoría de asignaciones reales como advertencia. La propia hoja ya documentaba la solución en su nota introductoria ("las columnas corresponden al mismo orden que la hoja Centros_Plataformas") — se cambió a emparejar por **posición**, verificado 1:1 contra las columnas/filas reales, con una comprobación defensiva que aborta con un mensaje claro si algún día el número de columnas no coincide con el de filas (en vez de emparejar mal en silencio). Esto casi triplicó las asignaciones detectadas.
2. Un trabajador del Excel real tiene un DNI en formato NIE (`Z2048304K`, extranjero) en la hoja `Empleados`, no `Extranjeros`. `Trabajador.EstablecerDni` (Fase 2) solo acepta el formato DNI (`\d{8}[A-Z]`), no NIE — se omite correctamente con motivo explícito en el reporte en vez de fallar la importación completa. Soportar NIE es una mejora de dominio real y legítima, pero fuera de alcance de esta fase (afectaría a todo el módulo Trabajadores, no solo a la importación) — queda anotado para v1.1.

**Criterio de aceptación**: el archivo Excel real se importa completo (36 Clientes, 36 Centros, 1 Empresa, 24 Trabajadores, 242 Documentos, 215 Asignaciones), con un reporte claro de qué se importó, qué se omitió y por qué (4 advertencias, 4 omitidos, cada uno con motivo). Verificado también que reimportar el mismo archivo no duplica nada.

## Fase 6 — Rediseño de identidad visual ProjectHydra

✅ Completa (primera pasada). Tras cerrar las 5 fases de v1, se recibió el brief de marca "ProjectHydra Platform Redesign" — realinear la identidad visual con ProjectHydra (60% identidad ProjectHydra, 20% estructura Stripe Dashboard, 10% minimalismo Notion, 10% pulido Linear), sin tocar arquitectura ni funcionalidad. Ver `DESIGN_SYSTEM.md` para el detalle completo de tokens; aquí solo el resumen de qué se tocó y qué queda pendiente.

- **Tokens** (`tokens.css`): nueva paleta (primario navy `#0D4E89`, secundario teal `#2FB8C6`), escala tipográfica H1–H4/Body/Small/Caption explícita, radios reestructurados en 5 niveles (`sm` 8px / `md` 12px / `card-sm` 16px / `lg` 20px / `full`), sombras mucho más suaves (`0 8px 30px rgba(15,23,42,.05)`), tokens de `motion` (150/200/250ms) nuevos. Los **nombres** de variable se mantuvieron estables — más de 50 archivos ya las consumían — solo cambiaron los valores, evitando una migración masiva y el riesgo que conlleva.
- **Componentes restilizados**: Boton (padding 14×24, radio 12px, elevación sutil en hover), CampoTexto/CampoSelect/CampoTextarea (min-height 48px, radio 12px, foco con outline sólido + glow suave — el outline sigue siendo el indicador accesible real, el glow es decorativo), Tarjeta (radio 20px), TarjetaMetrica (radio 16px), Toast (radio 16px + entrada con fade/slide), tablas (`list-page.css`: filas más espaciosas, cabecera sticky en mayúsculas con tracking, hover suave).
- **Iconografía**: primer set de iconos outline del proyecto (`Icono.razor`, SVG inline propio, sin librería externa — trazo 1.75px estilo Lucide/Heroicons), integrado en el sidebar (16 iconos) y en el botón de búsqueda global. Antes no había ningún icono en la navegación.
- **Verificado visualmente en navegador**: Login, Dashboard, un listado con QuickGrid (Clientes), un Drawer de creación con foco visible, Reportes, Calendario, el overlay del buscador global.

Un bug real encontrado al verificar: **los inputs de la pantalla de Login llevaban toda la vida del proyecto sin ningún estilo aplicado** (altura nativa del navegador ~21px, sin radio). Causa: `Login.razor` usa `<InputText>` de Blazor (componente hijo), y su CSS aislado (`Login.razor.css`) seleccionaba `input` directamente sin `::deep` — la CSS isolation de Blazor solo aplica el atributo de scope a elementos escritos directamente en el propio archivo `.razor`, no a los que renderiza un componente hijo por dentro. El resto de formularios de la app nunca tuvo este problema porque usan los componentes propios `CampoTexto`/`CampoSelect` (que sí escriben su `<input>`/`<select>` directamente). Corregido añadiendo `::deep` a los selectores de Login.razor.css.

Pendiente para una siguiente pasada (no bloquea, documentado en `DESIGN_SYSTEM.md` → "Pendientes"): componentes Chip, Tooltip, Tabs, Breadcrumb y un componente de Charts real (Dashboard hoy solo tiene KPIs numéricos y tablas, sin visualización gráfica); selector de tema claro/oscuro visible en la UI (los tokens ya están preparados para `prefers-color-scheme`, falta el control); guía de fotografía corporativa (no aplica todavía — la app no tiene pantallas de marketing).

## Fase 7 — Ajustes de usabilidad post-lanzamiento

✅ Completa. Cinco peticiones puntuales tras usar la app en el día a día.

- **Plantilla de importación masiva de Clientes** (`/clientes/importar`, Administrador): a diferencia del importador de Fase 5 (multi-hoja, formato completo de importación CAE), esta es una plantilla de una sola hoja (`Cliente / Centro`, `Crítico`, `Dirección`, `Contacto`) pensada para dar de alta rápidamente el resto de la cartera de clientes. Reutiliza `EjecutarImportacionCommand` de Fase 5 sin cambios (ya trataba `ClientesCentros` de forma genérica) — solo se añadió un parser nuevo (`ClosedXmlPlantillaClientesService`) y un endpoint de descarga de plantilla en blanco (`/clientes/plantilla.xlsx`, con una fila de ejemplo marcada para borrar). Mismo flujo Analizar → revisar plan → confirmar → reporte que Fase 5.
- **Espaciadores en el menú lateral**: gap entre ítems del sidebar de 4px a 8px.
- **Trabajadores por Empresa sin pasar por el buscador de texto**: se añadió un selector `Empresa` (dropdown estructurado, no búsqueda) a la barra de filtros de `/trabajadores`, con su propia Query (`ObtenerTrabajadoresQuery.EmpresaId`). Antes solo existía la búsqueda libre por nombre/apellidos/DNI, sin ninguna forma de ver la plantilla completa de una empresa concreta.
- **Búsqueda de trabajador en tiempo real**: verificado que ya funcionaba sin necesidad de Enter (el `oninput` de `CampoTexto` ya dispara la búsqueda en cada pulsación) — no requirió cambio de código, solo verificación explícita en navegador.
- **Paginación en todas las páginas de listado**: auditadas todas — Clientes/Empresas/Centros/Trabajadores/Documentos/Asignaciones ya tenían QuickGrid+Paginator (Fase 1-2). Se añadió paginación (en memoria, sobre la lista ya cargada — estos módulos no tenían Query paginada en servidor y el volumen de datos no lo justifica) a Tipos de Documento, Alertas, Usuarios y la vista previa de Reportes, con un componente nuevo reutilizable `PaginadorSimple.razor` (Anterior/Siguiente + "Página X de Y") que también reemplazó la implementación duplicada que ya tenía Auditoría. Sin cambios en Roles (4 tarjetas fijas, no es una lista dinámica) ni en Auditoría (ya paginaba, solo se centralizó su UI).

## Fase 8 — Menú lateral como botones + progreso con mensajes en importaciones

✅ Completa. Dos peticiones de pulido tras usar la app: el sidebar "se veía horrible" y las importaciones (Fase 5 y Fase 7) no comunicaban nada durante los segundos de espera.

- **Menú lateral rediseñado como botones**: `NavMenu.razor.css` reescrito — radio de `--radius-sm` (8px) a `--radius-md` (12px), borde transparente que se revela en hover, sombra suave en hover, y feedback táctil real con `.nav-item:active { transform: scale(0.97); transition-duration: 80ms; }` (el ítem "cede" ligeramente al pulsar y suelta al soltar). Se quitó el acento de barra izquierda (`::before`) del estado activo en favor de un fondo tintado (look de "botón seleccionado"), consistente con el resto del sistema de diseño.
  - **Bug real encontrado al verificar**: los selectores `.nav-item` no llevaban `::deep`, así que nunca aplicaron — `<NavLink>` es un componente hijo de Blazor (como `<InputText>` en el bug ya documentado de `Login.razor` en Fase 6) y el `<a>` que renderiza internamente no recibe el atributo de scope de CSS isolation de `NavMenu.razor`. El sidebar llevaba toda la vida del proyecto como enlaces sin estilo (azules, subrayados, sin iconos alineados). Corregido reescribiendo todos los selectores como `.nav-principal ::deep .nav-item...` (ligados al `<nav class="nav-principal">`, que sí es una etiqueta literal de este componente). ## Fase 26 — Bug de producción: límite de logs de Railway superado al sembrar datos de prueba

✅ Completa. Tras activar `DatosPrueba__Activo=true` en Railway (ver Fase 25/backlog #1), el arranque disparó el límite de Railway de 500 logs/seg y llegó a descartar más de 26.000 mensajes (`Railway rate limit of 500 logs/sec reached for replica`).

## Fase 27 — Dos bugs reales de producción encontrados probando en Railway: tema que no persiste y ripple que crece sin límite

✅ Completa. El usuario, probando ya sobre Railway, reportó dos comportamientos rotos.

**1. El tema (claro/oscuro) se reiniciaba al navegar entre secciones.** Causa: la navegación "enhanced" de Blazor (la que dispara cualquier clic en el menú lateral) vuelve a pedir al servidor el HTML de la página destino y hace un *morph* del DOM contra ese HTML nuevo — que nunca incluye `data-theme` en `<html>`, porque ese atributo solo lo pone `wwwroot/js/tema.js` en el cliente tras conectar el circuito. El morph lo borra en cada navegación, y como `SelectorTema.razor` vive en el layout persistente (no se vuelve a montar), su `OnAfterRenderAsync(firstRender: true)` — el único punto donde se reaplicaba — no vuelve a dispararse.
- **Arreglado**: `tema.js` ahora guarda el último tema aplicado en una variable de módulo y escucha el evento `Blazor.addEventListener('enhancedload', ...)` (el evento oficial de Blazor tras cada navegación enhanced) para reaplicarlo, sin depender de que ningún componente C# se vuelva a montar.
- **Verificado en navegador con Playwright**: tema puesto en "Oscuro", navegado por 5 secciones distintas (Clientes, Empresas, Trabajadores, Dashboard, Documentos) — `data-theme="oscuro"` se mantiene en las 5.

**2. El ripple de `.boton` se acumulaba sin límite y el botón parecía "crecer".** Causa real, distinta de lo que parecía a simple vista: `.boton-ondulacion` estaba definido en `Boton.razor.css`, un archivo de CSS **aislado** de Blazor — el compilador reescribe todo selector ahí a la forma `.clase[b-xxxxxxxx]` (el mismo atributo de scope que lleva el `<button>`). El `<span class="boton-ondulacion">` lo crea JS puro (`document.createElement`, ver `wwwroot/js/microinteracciones.js`) para no pagar JS interop por instancia — y un elemento creado fuera del árbol de Razor **nunca recibe ese atributo de scope**, así que la regla aislada nunca lo alcanzaba: sin `position: absolute` (quedaba en `position: static` por defecto) el span caía en flujo normal dentro del `inline-flex` del botón, con el ancho/alto grande que le fija el JS inline — inflando el botón en cada clic. Y como la regla con `animation:` tampoco lo alcanzaba, la animación nunca llegaba a aplicarse de verdad, `animationend` nunca disparaba, y el span nunca se quitaba — de ahí la acumulación.
- **Arreglado**: movido `.boton-ondulacion` + `@keyframes expandir-ondulacion` + su bloque de `prefers-reduced-motion` de `Boton.razor.css` a `wwwroot/css/base.css` (global, sin aislar) — mismo patrón ya usado para el revelado escalonado (`list-page.css`), que tiene el mismo problema de fondo (clases aplicadas a filas de `QuickGrid`, fuera del árbol de Razor del componente que las estilizaba). Además, `microinteracciones.js` ahora omite crear el span si `prefers-reduced-motion: reduce` está activo (coherente con el CSS) y añade un `setTimeout` de 650 ms como red de seguridad por si `animationend` no dispara por cualquier otro motivo (pestaña en segundo plano, etc.) — no depende ya de un único mecanismo de limpieza.
- **Verificado en navegador con Playwright**: 6 ciclos de abrir/cancelar el formulario de Empresas — antes dejaban spans creciendo sin límite (confirmado en un script de reproducción: 251px → 614px → 1286px → 1842px → 2622px de ancho); ahora quedan **0 spans** tras los 6 ciclos, y el ancho del botón "+ Nueva empresa" es idéntico antes y después (179.5625px ambas veces).

`dotnet build` sin errores, 90/90 tests en verde.

## Fase 32 — Documentos: conversión de Word (.docx) a PDF con LibreOffice

## Fase 44 — Previsualización de documento en Revisión IA (y fix real de aislamiento multi-tenant en endpoints minimal API)

✅ Completa (2026-07-24). Pedido explícito del usuario ("de implementar una previsualización del documento a la hora de revisarlo... intentar que sea lo más óptima y no relentice la experiencia"), sobre `/documentos/revision-ia`.

- **Bug real encontrado y corregido, no cosmético**: al verificar en navegador, el iframe recibía 404 pese a que el documento existe y es visible. Causa raíz: `ITenantActual`/`ICurrentUserService` (`CaeManager.Web/Services/`) solo resolvían el usuario/tenant vía `AuthenticationStateProvider` (documentado como "mismo patrón fuera de un circuito de Blazor no hay AuthenticationState") — válido para páginas Blazor, pero **los endpoints minimal API** (`GET /documentos/{id}/archivo`, ya usado antes de esta fase por los enlaces "Ver PDF" de `Documentos.razor`/`Alertas.razor`) no corren dentro de un circuito, así que `AuthenticationStateProvider.GetAuthenticationStateAsync()` devolvía un principal anónimo pese a que `HttpContext.User` ya estaba correctamente autenticado por la cookie de Identity — el filtro global de tenant interpretaba "sin tenant" y devolvía cero filas (fallo cerrado funcionando exactamente como está diseñado, pero con una fuente de identidad incompleta). Es decir: **los enlaces "Ver PDF" ya existentes estaban rotos para cualquier usuario real en el build multi-tenant**, sin ningún test que lo cubriera (ninguna suite E2E navegaba de verdad a ese endpoint).
- **Fix**: `TenantActual`/`CurrentUserService` ahora intentan primero `AuthenticationStateProvider` (circuito de Blazor) y, si no hay uno o el usuario no viene autenticado por esa vía, caen a `IHttpContextAccessor.HttpContext.User` (poblado por la cookie de Identity en cualquier petición HTTP normal, con o sin circuito). `IHttpContextAccessor` registrado en `Program.cs` (`AddHttpContextAccessor()`). ## Backlog — Capacidad: qué se rompe primero y en qué orden (analizado 2026-08-01, sin implementar)

Análisis pedido por el usuario ("¿qué pasa si nos hacen 200 request por segundo?"). **La unidad no aplica tal cual**: esto es Blazor Server, y salvo la carga inicial de página el usuario no hace peticiones HTTP — mantiene un circuito SignalR abierto por sesión. Lo que hay que dimensionar son *circuitos concurrentes* y *escrituras por segundo*, no req/s. 200 cargas de página nuevas por segundo y 200 interacciones por segundo repartidas entre usuarios ya conectados son escenarios con techos completamente distintos.

Los límites reales, por orden de aparición:

1. **Una sola réplica, y no por casualidad** (`DEPLOY.md` § 115). Tres cosas atan el proceso a su máquina: SQLite es un archivo en el volumen, los PDFs son archivos en el volumen, y los circuitos de Blazor son estado en memoria del proceso. No hay "subir réplicas" como salida rápida — ver la sección siguiente.
2. **SQLite sin WAL.** No hay ninguna `PRAGMA journal_mode=WAL` en el código: se usa el modo por defecto (rollback journal), donde un escritor bloquea a los lectores del archivo entero. Las escrituras se serializan y las lecturas esperan detrás. Activar WAL es de las intervenciones más baratas que quedan (los lectores dejan de bloquearse con el escritor) y **no espera a PostgreSQL**.
3. **Cola de análisis IA sin límite** (`ColaAnalisisDocumentoEnMemoria`: `Channel.CreateUnbounded`, `SingleReader = true`). Una punta de subidas encola sin techo —la memoria crece hasta donde llegue— y se procesa de uno en uno. Además vive en memoria: un redespliegue pierde todo lo encolado sin dejar rastro para el usuario que subió el documento.
4. **Conversión de Word serializada globalmente** (`LibreOfficeConversorWordPdfService`, `SemaphoreSlim(1,1)`): un `.docx` de un tenant hace esperar a los de todos los demás, y cada conversión levanta un proceso `soffice`.
5. **Sin rate limiting en ningún sitio** — no hay `AddRateLimiter` en `Program.cs`. El login y la subida de archivos están abiertos al ritmo que quiera el cliente. Es tanto un problema de capacidad como de seguridad (fuerza bruta).
6. **Todo comparte el mismo volumen**: base de datos, PDFs subidos, claves de Data Protection y los logs de Serilog con rotación diaria. Bajo carga, escribir logs compite por I/O con escribir en la base de datos.

**Qué es barato y no depende de la migración**: WAL + `busy_timeout` explícito, acotar la cola de IA con una política de rechazo consciente, rate limiting en login y subida, y límites de circuito de Blazor (retención de circuitos desconectados, lotes de render sin confirmar). **Qué no tiene arreglo barato**: todo lo demás es la migración a PostgreSQL y la salida del estado del proceso.

**Sin medir todavía**: no hay ninguna prueba de carga ejecutada contra el sistema, así que cualquier cifra concreta de "aguanta N usuarios" sería inventada. Lo de arriba es análisis de código, no medición.

## Fase 61 — Dos bugs reales de Blazor Server destapados por PostgreSQL (2026-08-01)

El primer arranque contra PostgreSQL destapó dos fallos que **ya existían** sobre SQLite pero nunca afloraban, porque las operaciones "async" de Microsoft.Data.Sqlite completan de forma síncrona y Npgsql hace I/O asíncrona real:

- ✅ **Carrera de DbContext entre componentes** ("A second operation was started on this context instance", reproducida en el login): durante el renderizado, MainLayout (guard de contraseña con `UserManager`), `SelectorTema`, `SelectorClienteActivo` y la página se inicializan en paralelo compartiendo el mismo `CaeManagerDbContext` scoped. Solución: `PuertaAccesoDatos` (Application) — serialización por scope, reentrante por flujo asíncrono para los Send anidados (`ObtenerKpisGlobalesQuery`) — aplicada en dos frentes: `SerializacionAccesoDatosBehavior` como primer behavior del pipeline de MediatR (cubre todas las páginas que solo usan Mediator), y envoltura explícita en los accesos que no pasan por MediatR (`MainLayout`, `SelectorTema`, `TrazaSoporteService`, `DirectorioUsuariosTenant`, y las páginas con `UserManager` directo: Usuarios, Roles, Auditoria, Delegaciones). **Regla para código nuevo**: cualquier acceso a datos desde un componente que no pase por MediatR tiene que envolverse en la puerta.
- ✅ **Bucle infinito de recargas de QuickGrid** (páginas de listado colgadas sin error, consultas repitiéndose decenas de veces por segundo): pasar el grupo de método directamente en el markup (`ItemsProvider="ProveerElementosAsync"`) crea un delegado nuevo en cada render; QuickGrid compara por referencia, lo trata como "fuente de datos distinta" y recarga — y el `StateHasChanged()` del proveedor garantiza el siguiente render. Con SQLite el ciclo no se disparaba (proveedor síncrono); con Npgsql colgaba la página indefinidamente. Solución en las 11 páginas con QuickGrid: el delegado se crea **una vez** (`_proveedorElementos`, asignado en `OnInitialized`) — diagnóstico por bisección documentado en `Clientes.razor.cs`. **Regla para grids nuevos**: nunca pasar el ItemsProvider como grupo de método en el markup.

Verificación: 504 tests en verde (Domain 199, Application 109, integración 169 sobre PostgreSQL, bUnit 19, E2E 8 con navegador real sobre SQLite), `dotnet format` limpio, gate de migraciones pendientes de SQLite sin cambios.

11. **Inputs de texto con sensación de lag al escribir rápido**: probable causa — cada tecla dispara un round-trip al servidor por el circuit de SignalR (binding `ValorChanged` de `CampoTexto` en cada `@oninput`), y bajo Railway (latencia de red real, no localhost) esto se nota como si el sistema "autocorrigiera" con retraso. Solución típica: debounce en el cliente antes de notificar al servidor, o cambiar el binding de esos campos a `@bind:event="onchange"` en vez de `oninput` donde no haga falta reactividad por tecla. Confirmar primero si de verdad es esto midiendo el round-trip.
    - **Hecho y verificado en navegador (2026-07-16)**: añadido debounce de 300 ms dentro de `CampoTexto.razor` — el `oninput` sigue disparando el round-trip (inevitable en Blazor Server), pero ya no se llama a `ValorChanged.InvokeAsync` hasta que el usuario hace una pausa al escribir. Esto evita el efecto "autocorrección": antes, si la respuesta de una tecla anterior llegaba tarde bajo latencia real, Blazor volvía a fijar el atributo `value` del `<input>` con un valor desactualizado, pisando visualmente lo que el usuario ya había escrito después. **Regresión encontrada y corregida durante la verificación con Playwright**: al probar el flujo real de "escribir y pulsar Guardar" se descubrió que un clic rápido tras escribir podía llegar al servidor antes que el debounce, enviando la Razón social vacía y bloqueando el alta con "La razón social es obligatoria" pese a verse texto en el campo. Se añadió `@onblur` en `CampoTexto.razor` que cancela el debounce pendiente y notifica el valor ya mismo al perder el foco (ocurre antes que el clic en Guardar en el orden de eventos del navegador). Verificado de nuevo: escribir rápido y guardar ya no falla, y la búsqueda en vivo sigue filtrando correctamente escribiendo a máxima velocidad.

12. **Feature — email de bienvenida al crear Usuario**: al dar de alta un Usuario (`/usuarios`) debe enviarse un correo con el link de acceso y las credenciales. ([Issue #2](https://github.com/christopherjp1-jpg/Project-Hydra/issues/2))
    - **Nota (2026-07-16)**: ProjectHydra ya paga licencias de Microsoft 365/Outlook — antes de dar de alta un proveedor nuevo (SendGrid, etc.), evaluar Microsoft Graph API (`sendMail`) o SMTP de Exchange Online con esas mismas licencias, para no pagar dos veces por envío de correo. Pendiente de implementar — no se tocó en esta sesión.

13. **Bug: plantilla descargable no aparece en `/importacion`**: la página de importación masiva debería ofrecer un enlace/botón para descargar la plantilla Excel (Fase 5/18) y no está apareciendo. Reproducir y revisar `Importacion.razor` y los servicios `IPlantillaClientesService`/`IPlantillaCombinadaService`/`IPlantillaDocumentosService` (¿el endpoint de descarga está registrado? ¿el botón está condicionado a algo que ya no se cumple?).
    - **Investigado y verificado en navegador (2026-07-16)**: no era un bug de código — `/importacion` (Fase 5, formato completo multi-hoja CAE) nunca tuvo plantilla en blanco a propósito, porque procesa un archivo de importación existente (ver "Fuera de alcance de v1").
